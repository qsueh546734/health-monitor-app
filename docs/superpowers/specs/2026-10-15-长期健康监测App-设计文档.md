## 1. 背景与目标

### 1.1 作品是什么

一个**长期健康监测终端 + 配套手机 App**：

- **采集**：GY-906 红外体温、MAX30102 心率（血氧后续）、MPU6050 计步、WaterSensor 水位
- **执行**：蜂鸣器 + LED 报警；TB6612 驱动水泵，水位低于阈值自动注水
- **主控**：STM32F103C8T6，本地 OLED 显示，拨动开关一键启停，独立电源供电
- **通信**：**ESP8266-01S WiFi**（与上个项目的蓝牙有本质区别）
- **App**：本地登录、实时数据、阈值设置、报警、历史曲线、**DeepSeek 数据分析**

### 1.2 成功标准

1. 答辩现场：手机连上 ESP8266 → 看到 5 项实时数据在刷新
2. 体温/心率超阈值或水位过低时：**设备端蜂鸣器+LED 响**，**App 端弹窗+卡片标红+响声音**
3. 水位低于阈值时水泵自动启动；App 可手动干预
4. 历史曲线能看出趋势，数据不丢
5. 分析页能给出一段 AI 健康总结，并能继续追问
6. 断网、模块复位、数据超时都不会让 App 卡死或显示错值

### 1.3 硬约束

| 约束 | 影响 |
|---|---|
| **现场没有可用路由器** | 默认走 **ESP 自开热点（AP）**；STA 作为"有网时更好"的加成 |
| **手机连 ESP 的 AP 后可能走不了移动数据** | DeepSeek 可用性受威胁 → **P0 必须实测**（§13 风险 1） |
| **用户从未刷过 ESP8266** | 刷写指南必须自包含、逐步可执行；供电是主要坑（§4.4） |
| **不做 iOS**，只做 Android | 沿用上个项目 |
| **本机没有 Android SDK** | 沿用云构建 + 纯 Java 本地测试（见 §7.1） |
| **零第三方依赖** | 图表必须**自绘 Canvas**，数据库用 `android.database.sqlite` |
| **不做数据聚合**（用户已同意砍掉） | 实际只跑几十分钟，2400 条原始数据足够；改为"上限淘汰" |
| **登录放 P2**（用户已同意） | 但数据库结构预留用户表，后续可无痛加入 |
| 固件分工：ESP 归本项目，STM32 归同学 | 协议是两边的**唯一契约**（§3） |

### 1.4 明确砍掉的（YAGNI）

数据聚合归档、后台/退出后报警、云端存储、iOS、多用户隔离、血氧（P2 前不做）、GPS、远程外网访问。

## 3. 应用协议规范（STM32 ↔ App）

> **§3 可整段复制给同学**，它是自包含的。

### 3.1 传输层

**TCP over WiFi**，不是蓝牙。与上个项目的唯一区别在传输层 —— **上层帧格式完全沿用**，因此 App 端的解析代码可以大部分复用。

- ESP8266 跑 **TCP 服务器**，默认端口 **8266**
- App 作 **TCP 客户端** 连入
- 字节流语义与串口相同：**没有消息边界**，必须靠 `\n` 分帧

> **这条最关键**：TCP 和串口一样是字节流，一次 `read()` 可能拿到半帧、也可能拿到两帧半。上个项目为此写的 `LineAssembler` **可以原样复用**。

### 3.2 帧格式总则

| 规则 | 约定 |
|---|---|
| 编码 | ASCII 文本，**人可读** |
| 帧起始 | `$` |
| 帧结束 | `\n`（0x0A）。**禁止 `\r\n`**；解析端仍容错剥离 `\r` |
| 字段分隔 | `,` |
| 键值分隔 | `=` |
| 校验分隔 | `*`，后接 2 位大写十六进制 |
| 帧类型 | 第 2 个字符：`D`=周期数据，`I`=设备信息（ESP→STM32 内部用），`C`=下行命令 |
| 小数格式 | 固定 **1 位小数** |
| **无效值** | 用 `--`（**不能发 0**） |
| 长度上限 | 单帧 ≤ **128 字节** |

### 3.3 上行周期数据帧 `$D`（STM32 → App，1 秒 1 帧）

```
$D,SEQ=123,BT=36.5,HR=72,SPO2=98,STEPS=1234,WATER=68,PUMP=0,PMODE=2,SW=1,AL=0,BTHI=37.3,HRHI=100,WLOW=20,*00
```

| 字段 | 含义 | 类型 | 单位 | 取值范围 |
|---|---|---|---|---|
| `SEQ` | 帧序号，每帧 +1，回绕 | uint16 | — | 0–65535 |
| `BT` | 体温（GY-906） | 1 位小数 | °C | 30.0–45.0，无效 `--` |
| `HR` | 心率（MAX30102） | uint16 | bpm | 30–220，无效 `--` |
| `SPO2` | 血氧（MAX30102） | uint16 | % | 70–100，无效 `--`（P2 前固定发 `--`） |
| `STEPS` | 累计步数（MPU6050） | uint32 | 步 | 0–999999 |
| `WATER` | 剩余水位 | uint8 | % | 0–100 |
| `PUMP` | 水泵**实际**状态 | uint8 | — | 0=关 1=开 |
| `PMODE` | 水泵**控制模式** | uint8 | — | 0=手动关 1=手动开 2=自动 |
| `SW` | **拨动开关** | uint8 | — | 1=系统运行 0=系统停止 |
| `AL` | 报警位域 | uint8 | — | 见 §3.4 |
| `BTHI` | 体温上限阈值 | 1 位小数 | °C | 供 App 回读 |
| `HRHI` | 心率上限阈值 | uint16 | bpm | 供 App 回读 |
| `WLOW` | 水位下限阈值 | uint8 | % | 供 App 回读 |
| `*CS` | 异或校验 | 2 位十六进制 | — | 第一版固定 `00`，见 §3.7 |

**`SW=0`（拨动开关关掉）时的特殊约定**

STM32 **仍然每秒发一帧**，但只带这几个字段：

```
$D,SEQ=124,SW=0,AL=0,*00
```

其余字段**全部省略**。App 收到后显示「系统已停止」，并**把其余卡片置灰**，而不是显示旧值或 `--`。

> **为什么这样设计**：如果关掉开关就完全停发，App 分不清「用户主动关机」和「链路断了」—— 前者是正常状态，后者要报警。多发一行零成本的帧就能区分，这是 Key=Value 协议对缺字段天然容错的直接收益。

### 3.4 `AL` 报警位域

| 位 | 值 | 含义 | 触发条件 |
|---|---|---|---|
| bit0 | `0x01` | 体温异常 | `BT > BTHI` |
| bit1 | `0x02` | 心率异常 | `HR > HRHI` |
| bit2 | `0x04` | 水位过低 | `WATER < WLOW` |
| bit3 | `0x08` | 传感器故障 | 任一路读取失败，或系统异常 |

`AL=0` 全部正常；多位同时触发按位或。App 按位显示对应的红色卡片与提示文案。

### 3.5 下行命令帧 `$C`（App → STM32）

```
$C,CMD=<命令名>[,参数=值...],*00
```

| CMD | 参数 | 取值范围 | STM32 行为 | App 触发 |
|---|---|---|---|---|
| `TH` | `BTHI`,`HRHI`,`WLOW` | BTHI 35.0–42.0；HRHI 60–180；WLOW 0–100 | 更新阈值并保存 | 设置页【下发】 |
| `PUMP` | `MODE` | 0=手动关 1=手动开 **2=自动** | 切换水泵控制模式 | 主控页水泵开关 / 【恢复自动】 |
| `QUERY` | — | — | 立即补发一帧 `$D` | 连接成功后自动发一次 |
| `CLRSTEPS` | — | — | 累计步数清零 | 设置页【步数清零】 |

**命令示例**

```
$C,CMD=TH,BTHI=37.3,HRHI=100,WLOW=20,*00
$C,CMD=PUMP,MODE=2,*00
$C,CMD=QUERY,*00
$C,CMD=CLRSTEPS,*00
```

> **水泵的三态设计**：`MODE=2`（自动）是默认状态 —— 水位低于 `WLOW` 自动开、回到 `WLOW+10` 自动关（**加 10% 回差防止在阈值处反复启停**，这是真实设备必须做的）。App 手动开/关会把模式切成 0/1，界面上必须显示当前是"自动"还是"手动"，并提供【恢复自动】。

### 3.5.1 ESP 专属命令（被 ESP8266 拦截，STM32 看不到）

以下三条命令**只到 ESP8266 为止**，ESP 拦截后不会转发给 STM32。它们解决"WiFi 凭据写死在固件里、每换网络都要重新烧录"的问题。

| CMD | 参数 | ESP 行为 | App 触发 |
|---|---|---|---|
| `WIFI` | `SSID`,`PASS` | 尝试连接 → 成功则保存并重启进 STA；失败则**不保存**、留在热点模式并回复原因 | 设置页【连接路由器】 |
| `WIFIFORGET` | — | 清空已保存凭据 → 重启回热点模式 | 设置页【忘记网络】 |
| `WIFISTATUS` | — | 立即回一帧 `$I` | 进入设置页 / 连接成功后 |

```
$C,CMD=WIFI,SSID=MyRouter,PASS=abc12345,*00
$C,CMD=WIFIFORGET,*00
$C,CMD=WIFISTATUS,*00
```

**🔑 安全设计（三条缺一不可）**

1. **只有连接成功才保存凭据** —— 密码打错不会被写入 Flash，所以永远不会把自己锁死在连不上的网络上
2. **配置过程中保持热点开着**（`WIFI_AP_STA`）—— 尝试期间不失去连接，还能把失败原因回给 App
3. **开机 STA 失败自动回落 AP** —— 就算凭据本身没问题但路由器不在，断电重启 10 秒后一定能回到 `HealthMon`

**配置流程**

```
① 手机连 HealthMon（此时 ESP 是 AP 模式）
② App 发 $C,CMD=WIFI,SSID=...,PASS=...
③ ESP 回 $I,...,WIFI=TRYING,*00        ← 最多要等 15 秒，App 要显示"连接中"
④ 成功：回 $I,IP=<新IP>,PORT=8266,MODE=STA,WIFI=OK,*00
        → 保存凭据 → 重启 → 以 STA 模式运行
   失败：回 $I,...,MODE=AP,WIFI=FAIL,RSN=<原因>,*00
        → 回到纯热点模式，不保存
⑤ App 收到 OK 后提示用户：把手机也连到同一个路由器，再填新 IP 连接
```

**失败原因码 `RSN`**

| 值 | 含义 | 用户该怎么做 |
|---|---|---|
| `NOSID` | 找不到这个 WiFi | 检查名字、确认是 2.4G 频段 |
| `PWD` | 密码错 | 重输密码 |
| `CONNFAIL` | 连接失败 | 检查路由器是否限制了设备数 |
| `TIMEOUT` | 超时 | 重试 |
| `NOSSI` | SSID 为空 | 填上名字 |

> ⚠️ **限制**：SSID 和密码里**不能含逗号 `,`**（会破坏 Key=Value 解析）。家用路由器基本不会遇到。

> ⚠️ **ESP8266 只支持 2.4GHz**，5G 网络连不上 —— 这是芯片限制，不是固件问题。

### 3.6 隐式 ACK：靠状态回显确认

**不设独立应答帧。** App 靠下一帧 `$D` 的状态字段判断命令是否生效：

| 命令 | 判据（**必须是命令之后新到的帧**） |
|---|---|
| `TH,...` | `BTHI`/`HRHI`/`WLOW` 变为新值 |
| `PUMP,MODE=n` | `PMODE` 变为 n（**不是**看 `PUMP`，因为自动模式下水泵会随水位自己动，单看 `PUMP` 会误判） |
| `QUERY` | 收到新的 `SEQ` |
| `CLRSTEPS` | `STEPS` 变为 0 |

> **上个项目踩过的坑，这次直接规避**：判据不能是"当前值等于期望值"，否则「命令根本没发出去」也会因为残留状态而显示"已确认"。App 端实现必须记录**命令发出时的收帧计数**，只有之后新到的帧才允许判定确认。详见 §7.4。

### 3.7 校验字段

异或校验：范围是 `$` 与最后一个 `*` 之间的所有字符，逐字节 XOR，取 2 位大写十六进制。

**第一版一律填 `*00`**，App 视为"未启用校验"并正常处理。非 `00` 时：校验不一致**只计数、不丢帧**，并在统计栏显示"校验错 N"。这让启用校验成为纯增量、可回退的动作。

### 3.8 序号与丢帧统计

STM32 每帧 `SEQ` +1（uint16 回绕）。App 端：

- 序号连续 → 正常
- **回绕**（65535→0）→ 不算丢帧
- **重复帧**（同序号重复到达）→ 不算丢帧
- **大幅回退**（如 300→42，设备复位）→ 重新同步，**不虚报丢帧**
- 其余跳变 → 计入丢帧数，显示"已收 N 帧 / 丢 M 帧"

四种情况都必须正确处理 —— 上个项目在此处出过"丢 65277 帧"的假数据。

## 4. 网络与 ESP8266

### 4.1 双模式与自动切换

```
ESP8266 上电
  ├─ 尝试 STA：连配置好的 WiFi（有路由器时走这条）
  │    10 秒超时或失败 ↓
  └─ 自动转 AP：自开热点
        SSID     : HealthMon
        密码     : 12345678
        固定 IP  : 192.168.4.1
        端口     : 8266
```

**为什么 AP 是现场默认**：用户的现场没有路由器。AP 模式的最大好处是 **IP 固定 `192.168.4.1`，零发现逻辑**，写死在 App 默认值里即可。

### 4.2 IP 发现：用 OLED，不写发现协议

STA 模式下 ESP 拿到的是 DHCP 地址，App 不知道它是什么。三种解法对比：

| 方案 | 成本 | 可靠性 |
|---|---|---|
| UDP 广播发现（App 广播、ESP 应答） | 两边各约 20 行 | 高，但热点子网可能屏蔽广播 |
| 扫描整个 /24 网段 | 慢（几秒到几十秒） | 中 |
| **OLED 显示 IP，App 里手填一次** | **几乎为零** | **最高** |

**选定第三种**：ESP 把 IP 通过串口告诉 STM32（§4.5 的 `$I` 帧），STM32 显示在 OLED 上。用户看一眼、在 App 设置页填一次即可。答辩时这也是个能讲的细节。

### 4.3 TCP 服务端细节

- 端口 **8266**
- **允许 1 个客户端**（够用；多客户端会让"谁在控制水泵"变得含糊）
- 新客户端连入时，若已有客户端则**踢掉旧的**（现场重复连接很常见）
- 开启 `TCP_NODELAY`（关闭 Nagle）—— 小包低延迟
- **心跳**：App 每 5 秒没有数据往来就发一次 `$C,CMD=QUERY,*00`（顺带刷新数据，一举两得）
- 客户端断开后 ESP 不重启，继续等待新连接

### 4.4 🔴 ESP8266-01S 供电（本项目的头号硬件坑）

ESP8266 发射瞬间电流可达 **~300mA**，而多数 USB-TTL 的 3.3V 引脚只能提供 50–100mA。

**症状**：刷写进度条中途失败、反复 "Failed to connect"、运行中随机重启。

**必须做的三件事**：

1. **专用 3.3V 供电**：用独立稳压（如 AMS1117-3.3 小板）给 ESP 供电，**不要**从 USB-TTL 的 3.3V 引脚取电
2. **退耦电容**：ESP 的 VCC–GND 之间跨接 **100µF 电解 + 0.1µF 陶瓷**（这一步能解决绝大部分随机失败）
3. **量电压**：发射瞬间 VCC 对地不得低于 3.0V；低于就说明供电不足

> 详细的刷写接线与步骤见 `docs/hardware/ESP8266刷写指南.md`（独立自包含文档）。

### 4.5 串口协议（STM32 ↔ ESP8266，115200 8N1）

**只有 3 条，极简**：

| 方向 | 帧 | 含义 |
|---|---|---|
| ESP → STM32 **和 App** | `$I,IP=192.168.4.1,PORT=8266,MODE=AP,*00\n` | ESP 状态帧。状态变化时主动上报（上电、连上 WiFi、切换模式、客户端连入/断开），并作为 WiFi 配置命令的应答 |
| STM32 → ESP | 任意字节 | **原样透传给 TCP 客户端**（STM32 发的 `$D` 帧） |
| ESP → STM32 | 任意字节 | **原样透传自 TCP**（App 发的 `$C` 帧），**但 `WIFI`/`WIFIFORGET`/`WIFISTATUS` 三条会被拦截**（§3.5.1） |

**`$I` 帧字段**

| 字段 | 含义 | 取值 |
|---|---|---|
| `IP` | 当前本机 IP | 点分十进制 |
| `PORT` | TCP 端口 | 8266 |
| `MODE` | 当前模式 | `STA` / `AP` |
| `WIFI` | 配置结果（仅应答时有） | `TRYING` / `OK` / `FAIL` / `FORGOTTEN` |
| `RSN` | 失败原因（仅 `WIFI=FAIL` 时有） | 见 §3.5.1 |

> **为什么 `$I` 也发给 App**：App 需要显示当前模式和 IP；而 WiFi 配置的结果（成功/失败/原因）只能通过这条帧回给 App —— STM32 收到后只需更新 OLED，**不要**把它当成 App 的命令处理。

**关键实现点**：ESP 自己写进串口的 `$I` 行**只到 STM32**，不进"串口→TCP"转发方向 —— 这两个方向是独立的，天然不会串。

STM32 收到 `$I` 后：更新 OLED 上的 IP 显示，**不要**把它当成 App 的命令处理。

## 5. ESP8266 端固件设计

**开发方式**：Arduino IDE + `esp8266 by ESP8266 Community` 开发板包，板子选 `Generic ESP8266 Module`，Flash Size `1MB`，上传速率 `115200`。

**为什么刷固件而不是用 AT 指令**：刷固件是一次性成本（约半小时）；AT 指令意味着 STM32 侧要写 AT 响应解析、超时重试、状态机 —— 那是**持续性**的坑，且极难调试。

### 5.1 固件结构（单个 .ino）

| 部分 | 职责 |
|---|---|
| `setup()` | 串口 115200；尝试 STA（10 秒超时）→ 失败则 `softAP`；启动 TCP server；发送 `$I` 帧 |
| `loop()` | 双向透传 + 客户端管理 |
| `onSerial()` | 串口有数据 → 转发给所有已连接的 TCP 客户端 |
| `onClient()` | TCP 有数据 → 写入串口 |
| `sendInfoFrame()` | 组装并发送 `$I` 帧（IP/端口/模式） |

### 5.2 必须处理的边界

- **单客户端**：新连接踢掉旧的
- **`TCP_NODELAY`**：`client.setNoDelay(true)`
- **串口波特率 115200**：与 STM32 的 USART2 一致
- **AP 模式下也给手机分配 IP**：`softAP` 默认 DHCP 会分配 `192.168.4.2+`
- **不要在 `loop()` 里 `delay()` 阻塞**：会丢串口数据
- **看门狗**：ESP8266 的 `loop()` 必须持续返回，否则软看门狗复位

## 6. STM32 端固件设计（同学负责，本方案给出接口与要求）

### 6.1 外设分配

| 外设 | 用途 | 备注 |
|---|---|---|
| USART1 | 调试镜像（接电脑串口助手） | **强烈建议保留**，排障神器 |
| USART2 | **ESP8266** | 115200 8N1，PA2/PA3 |
| I2C1 | GY-906(0x5A) + MAX30102(0x57) + MPU6050(0x68) | **三个地址不冲突**，可挂同一总线 |
| ADC | WaterSensor | 模拟量 |
| GPIO | 蜂鸣器、LED、拨动开关 | 开关建议加软件消抖（20ms） |
| TIM + GPIO | TB6612 → 水泵 | PWM 调速 |

### 6.2 主循环骨架

```c
while (1) {
    while (BT_Poll(line, BT_LINE_MAX)) {   /* 复用上个项目的 BT.c 结构 */
        if (line[1] == 'I') { HandleInfoFrame(line); }   /* ESP 的 $I 帧 -> 更新 OLED */
        else                { Proto_ParseLine(line); }   /* App 的 $C 命令 */
    }
    Proto_Tick(g_ms);                       /* 看门狗 */
    sensors_update();                       /* 读四个传感器 */
    pump_control();                         /* 水位 + 回差 + 手动模式 */
    alarm_update();                         /* 蜂鸣器 + LED */
    oled_refresh();                         /* 显示数值 + IP */
    if (g_ms - lastReport >= 1000) { lastReport = g_ms; Proto_SendData(); }
}
```

### 6.3 硬要求

1. **中断里只塞环形缓冲，绝不 printf**
2. **上电时若 `SW=0`，仍要每秒发 `$D,SEQ=n,SW=0,AL=0`**（§3.3）
3. **水泵回差**：低于 `WLOW` 开，高于 `WLOW+10` 才关，防止阈值处反复启停
4. **传感器读取失败要发 `--`**，不能发 0
5. **调试镜像**：所有经 ESPN 发出的数据同时从 USART1 输出一份
6. **拨动开关消抖**：20ms 软件消抖，避免状态抖动导致 App 显示闪烁

### 7.3 数据库设计

```sql
-- 实时采样（1 Hz）
CREATE TABLE samples (
  id     INTEGER PRIMARY KEY AUTOINCREMENT,
  ts     INTEGER NOT NULL,      -- 毫秒时间戳
  bt     REAL,                  -- 体温（可空）
  hr     INTEGER,               -- 心率
  spo2   INTEGER,               -- 血氧
  steps  INTEGER,               -- 累计步数
  water  INTEGER,               -- 水位
  pump   INTEGER,               -- 水泵
  sw     INTEGER,               -- 拨动开关
  al     INTEGER                -- 报警位
);
CREATE INDEX idx_samples_ts ON samples(ts);

-- 用户（P2 登录用；P1 之前先建表不用）
CREATE TABLE users (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT UNIQUE NOT NULL,
  pwd_hash TEXT NOT NULL,
  salt     TEXT NOT NULL,
  age      INTEGER, gender TEXT, height REAL, weight REAL,
  created  INTEGER
);

-- 键值配置：阈值、IP、端口、API key 等
CREATE TABLE settings (k TEXT PRIMARY KEY, v TEXT);
```

**上限淘汰**：每插入 100 条检查一次，`SELECT COUNT(*)` 超过 **50000** 就 `DELETE FROM samples WHERE id IN (SELECT id FROM samples ORDER BY id LIMIT 1000)`。

> **为什么砍掉聚合**：实际只跑几十分钟（2400 条），聚合是白写。保留上限淘汰即可保证永不爆库。

### 7.4 隐式 ACK 的正确实现（吸取上个项目的教训）

```
命令发出时：baselineRecv = 当前 recvCount
判定确认时：必须先满足 recvCount > baselineRecv   ← 关键
            再比对状态字段是否变为期望值
```

**没有这个基线，会出现"命令根本没发出去却显示已确认"** —— 上个项目在急停按钮上出过这个问题。本次所有命令（含水泵手动控制）都走这个机制。

### 7.6 模拟器模式（开发期与演示期的双保险）

设置页开关。开启后 `Simulator` 按 1 Hz 产生与真实设备一致的帧（含偶发的体温升高、心率异常、水位下降），走**与真实网络完全相同的解析路径**。

1. **开发期**：ESP 还没刷好、STM32 还没接好，App 就能全部开发完并验证

**上下文构造**（控制 token 的关键）：

```
系统提示：你是健康数据分析助手，根据以下数据给出简明建议，不要诊断疾病。
```

## 8. 关键时序

### 8.1 首次连接

```
用户在手机 WiFi 里连上 HealthMon（密码 12345678）
  → 打开 App 连接页 → IP 默认 192.168.4.1、端口 8266 → 点【连接】
  → TCP 连接建立（3 秒超时）
  → App 发 $C,CMD=QUERY,*00\n
  → 收到第一帧 $D → 状态灯变绿，五张卡片开始刷新
  → 若 3 秒内没收到任何帧 → 显示「已连接但设备无数据」，而不是一直转圈
```

### 8.2 一次报警的完整路径

```
体温升到 37.8 °C（阈值 37.3）
  → STM32：AL bit0 置位；蜂鸣器响、LED 亮；下一帧 $D 带上 BT=37.8,AL=1
  → App：收到帧 → 体温卡片变红 → 弹窗「体温 37.8°C 超过阈值 37.3°C」+ 响一声
        → 若开历史页，曲线同步更新
  → 30 秒内不再重复弹窗（避免刷屏）
  → 体温回落后：STM32 清 bit0、关蜂鸣器；App 卡片恢复
```

### 8.3 水位自动补水（含回差）

```
WATER 降到 19%（阈值 20）→ AL bit2 置位 → 水泵开 → PUMP=1
  → App 上水泵显示「自动·运行中」
WATER 升到 30%（阈值+10）→ 水泵关 → PUMP=0 → AL bit2 清除
  ※ 回差 10% 防止在 20% 附近反复启停
```

## 9. 安全与异常处理

| 情况 | 处理 |
|---|---|
| **TCP 断连** | App 状态灯变红 + 提示；每 5 秒自动重连（最多 12 次后停止并提示手动重连） |
| **连上但收不到数据** | 3 秒无帧 → 显示「设备无数据」并保留重试；用户可切模拟器保底演示 |
| **数据超时 / 陈旧** | 每帧记录时刻，超 3 秒未更新时卡片显示灰色 + 「数据已 Xs 未更新」，**绝不把旧值当实时值显示** |
| **半帧 / 粘帧** | `LineAssembler` 累积 + 按 `\n` 切分（复用上个项目，已有 27 项断言） |
| **乱码行** | 必须 `$` 开头 + 能切出 key=value 才接受，否则丢弃并计数 |
| **`SW=0`（系统停止）** | 显示「系统已停止」，其余卡片置灰，**不报警**（这是用户主动行为） |
| **传感器无效值** | 显示 `--`，绝不用 0 代替 |
| **报警刷屏** | 同一报警 30 秒内只弹一次 |
| **水泵阈值抖动** | 固件侧 10% 回差（§8.3） |
| **DeepSeek 失败** | 15 秒超时；明确文案（网络/额度/格式）；不阻塞其他页面 |
| **App 退出** | `onDestroy` 里断开 TCP、移除定时器（上个项目漏过这个，本次从第一版就做） |
| **数据库膨胀** | 5 万条上限自动淘汰最旧 |

**阶段 0 实测结果（2026-10-15）**

| 项 | 结果 |
|---|---|
| ESP 刷写 | ✅ 成功（用 ESP8266 刷写器，一次通过） |
| 串口输出 | ✅ 正常（此前乱码是串口监视器波特率问题，非固件问题） |
| 手机搜到 `HealthMon` | ✅ 能搜到 |
| 网络调试助手连 `192.168.4.1:8266` | ✅ **能连上 —— TCP 链路完全打通** |
| **连着 `HealthMon` 时访问 `baidu.com`** | ❌ **打不开 —— 手机走不了移动数据**（AP 模式固有） |
| **ESP 连上手机热点（STA 模式）** | ✅ **成功** —— 需先解决 EEPROM 不落盘问题（见下） |
| **ESP 连热点后打开 `baidu.com`** | ✅ **能打开 —— 手机移动数据不受影响** |

**🔴 过程中发现并解决的一个真问题：Arduino EEPROM 在这块 ESP-01S 上不落盘**

现象：`WIFI=SAVED` 应答正常、`#saved, readback SSID=[iKUN 13] len=7` 回读也对，但 `ESP.restart()` 之后是 `#EEPROM: not initialised` —— 凭据没写进 flash。因此 ESP 重启后认为自己没有凭据，**压根没去连热点**（连 `#STA failed` 都不打印）。

**根因**：Arduino EEPROM 库使用的 flash 扇区与 ESP8266 SDK 自身的系统参数 / RF 校准区冲突，被开机流程覆盖。

**解决**：改用 SDK 自带的 WiFi 持久化（`WiFi.persistent(true)` + `WiFi.begin(ssid,pass)`），并增加一组**硬编码兜底凭据**（编译期开关 `USE_DEFAULT_WIFI`），彻底不依赖持久化机制。

> **教训**：这一条排查花了多轮，因为"写入成功"和"重启后仍在"是两件事，而中间隔了一次重启 —— 只有把「发命令 → 重启 → 再读」放在**同一次串口捕获**里才看得出来。

> 🔴 **结论：AP 模式下 DeepSeek 不可用。** 这是设计阶段就预判到的风险，现已实测确认。
> 应对方案见 §13 风险 1。**这不影响数据采集、实时显示、报警、曲线等所有本地功能。**

**0-4 不通过**的处理：AI 功能改为「临时切到移动数据再分析」，或明确接受 AI 功能只在有路由器时可用。

### 阶段 1：无硬件联调（D1–D2）

- App 用**模拟器模式**把五个页面全部开发完
- 电脑上用 Node 写一个**假 TCP 服务器**（复用协议），模拟 STM32 发帧

1. **只收**：STM32 只发 `$D`，App 只显示

| **D1–2** | — | STM32 发假数据（五个字段） | App 骨架 + 模拟器 + 五个页面 |
| **D3–4** | 装机验证 | 四个传感器调通 | TCP 客户端 + 实时数据页 + 假服务器联调 |
| **D5–6** | 真机联调（只收→只发→双向） | 水泵/报警/开关 | 真机联调 |
| **D7–8** | 验证报警与曲线 | 阈值与回差逻辑 | 阈值 + 报警 + 历史 + 曲线 |
| **D9–10** | 验证水泵手动干预 | OLED 显示 IP | 水泵控制 + 开关状态 + 用户信息 |
| **D11–12** | 验证 AI 分析 | 稳定性 | **DeepSeek 分析页 + 登录** |
| **D13–14** | 整体验收 + 报告素材 | 整机装配 | 打磨、截图 |

**P0 优先级**（时间不够时保这些）：ESP 刷通 → 阶段 0 → 实时数据页 → 报警 → 历史曲线
**P2 可延后**：DeepSeek、登录、血氧

## 12. 明确不做（YAGNI）

| 不做 | 理由 |
|---|---|

| 云端存储 | 本地 SQLite 已满足 |
| iOS | 用户只要求 Android |
| 多用户数据隔离 | 单人使用（用户已确认）；表结构预留 |

| UDP 自动发现设备 | OLED 显示 IP 更简单可靠 |
| 数据导出 CSV | 有曲线图后价值降低，有余力再说 |

## 13. 风险登记

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 🔴 **手机连 ESP 的 AP 后走不了移动数据**（**已实测确认会发生**） | **已发生** | **高**（AP 模式下 DeepSeek 不可用） | 三选一，见下方"风险 1 的应对"。**不影响本地功能** |
| 🔴 **ESP8266 刷写失败（供电）** | **高** | 高 | 专用 3.3V + 100µF 退耦电容；先刷眨眼固件验证工具链（§4.4 与硬件指南） |
| 🟡 **MAX30102 心率算法在 F103 上算力吃紧** | 中 | 中 | 血氧推后；心率先用现成库，不行就降级为"显示原始波形 + 占位值"，并在报告中说明 |
| 🟡 **同学的主板进度延误** | 中 | 高 | App 用模拟器独立完成 80%；假 TCP 服务器让它与真机解耦 |
| 🟡 **1–2 周内做不完全部功能** | 中 | 中 | P0/P1/P2 分级已定；P2 可整体延后 |
| 🟢 零依赖下自绘曲线 | 低 | 中 | Canvas 折线约 150 行，已有明确方案；必要时降采样 |
| 🟢 协议两端错位 | 低 | 中 | 沿用上个项目的跨语言测试思路：把 ESP/STM32 会产出的真实帧字面量喂给真正的 Java 解析器 |
| 🟢 数据库膨胀 | 低 | 低 | 5 万条上限自动淘汰 |

### 风险 1 的应对（已实测确认，三选一）

**问题**：手机一旦连上 `HealthMon`（ESP 的热点），它的 WiFi 就被占用了，系统不会自动回落到移动数据 —— 于是 DeepSeek 调不通。

**根因**：Android 把"已连接的 WiFi"当作默认网络，即使它没有外网。要绕开必须**让数据走另一条路**，或者**不要让手机连 ESP 的热点**。

| 方案 | 做法 | 可靠性 | 代价 |
|---|---|---|---|
| **A. 让 ESP 连手机热点**（推荐） | 手机开热点 → ESP 用 §3.5.1 的功能连上它 → 手机既是热点提供方又是客户端所在网段，**移动数据不受影响** | 高 | 几乎为零 —— 功能已实现 |
| **B. App 把 API 调用绑定到移动数据** | 用 `ConnectivityManager.requestNetwork(TRANSPORT_CELLULAR)` 拿到蜂窝网络，再用它的 `Network` 发 HTTP 请求 —— **即使 WiFi 连着 ESP 也能走流量** | 中（各 ROM 行为不一） | 中：约 50 行 + 需处理请求失败 |
| **C. 分析时手动切网** | 数据本来就存在手机 SQLite 里，**分析和采集本来就不需要同时进行**。切到移动数据 → 打开分析页 → 分析 | **最高**（零依赖） | 零代码，只需一句提示 |

**推荐组合：A 为主 + C 保底。**（**已选定 A**）

- **A 作为主路径**：热点模式下手机上网正常，所有功能同时可用。ESP 的 IP 从 **OLED** 上读（§4.2 已经这么设计了）
- **C 作为保底**：即使 A 不成立（比如运营商限制热点），数据也不会丢 —— 它是本地存储的。App 在分析页检测到"当前连接的是设备热点、无外网"时，直接提示：
  > 「当前连接的是设备热点，无法访问互联网。请在系统设置里切到移动数据，再回来点重试。」
- **B 是可选增强**：如果时间富余再做。它能做到"连着 ESP 也能分析"，体验最好，但要在多个 ROM 上测。

> **关键认识**：AI 分析**不需要**和 ESP 保持连接 —— 数据早就存在手机本地了。把"采集"和"分析"解耦，这个风险就自动降级成一个提示文案问题。

#### 方案 A 的操作顺序问题（2026-10-15 已实测，矛盾不存在）

**原担心**：配置时需要手机连 `HealthMon`，而 A 又要求手机开热点；多数安卓开启热点会关闭 WiFi，形成冲突。

**实测结果**：**该手机可以同时开热点 + 连 `HealthMon`** ✅ —— 矛盾不存在，**固件无需改动**，保持"只有连上才保存"的语义（更安全）。

**由此确定的部署形态**（家里/实验室都没有路由器，热点是唯一路径）：

```
配网（一次性）：
  ① 手机开热点（名字密码记下来）
  ② 手机连 HealthMon
  ③ 下发 $C,CMD=WIFI,SSID=<热点名>,PASS=<热点密码>,*00
  ④ ESP 连上热点 → 保存 → 重启进 STA 模式
  ⑤ 从【串口】读 ESP 的新 IP（如 192.168.43.xxx）
     —— STM32 做好后改从 OLED 读

使用（每次演示）：
  ① 手机开热点（凭据已存，ESP 开机自动连）
  ② 设备上电 → ESP 连上热点
  ③ App 连 ESP 在那个网段的 IP
  ④ 手机外网走移动数据 → DeepSeek 同时可用 ✅
```

> **不再需要**家里的路由器，也不再需要开发板当 AP。

#### ⚠️ 唯一剩余未知：手机能不能访问【自己热点下的客户端】

ESP 连上手机热点后，它的身份是"手机热点的客户端"（例如 `192.168.43.137`）。**手机 App 能不能访问这个地址，需要实测** —— 现代 Android 给每个 App 的流量做了网络绑定，热点子网的路由未必对 App 可见。

| 实测结果 | 含义 |
|---|---|
| **能连上** | ✅ 方案 A 完全成立，所有功能（含 DeepSeek）同时可用 —— **这是最好的结果** |
| 连不上 | ❌ 退回**方案 C**：采集时连 `HealthMon`，分析时切到移动数据。数据在本地，切网不丢。**功能不受损，只是演示时多切一次网** |

**实测步骤**（在做完上面的配网后）：

1. 手机用网络调试助手连 **`192.168.43.xxx:8266`**（IP 从 ESP 串口/OLED 读）
2. 能连上 → 发 `$C,CMD=QUERY,*00`，看是否收到 `$D` 帧
3. 同时打开浏览器访问 `baidu.com` 确认外网正常

**无论哪种结果，方案都不会失败** —— 差别只是"演示时要不要切一次网"。

## 附录 A：演示操作流程卡

> ⚠️ **方案 A（ESP 连手机热点）成功时**：全程手机都有网，第 9 步直接可用。
> **只有热点模式（ESP 开 AP）时**：手机连 `HealthMon` 期间**没有外网**，第 9 步需要先切网络。

**演示前准备（在家完成）**
- 手机已安装最新 APK
- 手机 WiFi 里已保存 `HealthMon`（密码 `12345678`）
- 设备已上电，OLED 显示 IP
- 手机已关闭"自动切换 WiFi"以外的干扰设置
- **决定走哪条路**：
  - 走热点方案 → 提前在 App 里把 ESP 配到手机热点上，记下 OLED 显示的 IP
  - 走 AP 方案 → 第 9 步前先切到移动数据做完 AI 分析

**现场流程**
1. 设备上电 → 确认 OLED 显示 IP 与传感器数值
2. 手机连 `HealthMon`（或连同一路由器/热点）→ 打开 App → 连接页填 IP → 【连接】
3. 主控页观察五项数据刷新
4. 用手捂住红外探头 / 做几个动作 → 体温或心率超阈值 → **三管齐下报警**
5. 历史页看曲线上升
6. 给水位传感器滴水 / 抽走水 → 水位下降 → 水泵自动启动 → App 显示"自动·运行中"
7. 手动关水泵 → 显示"手动·已停止" → 点【恢复自动】
8. 拨动开关关掉 → App 显示「系统已停止」→ 再打开
9. **AI 分析**：
   - 走热点方案 → 直接进分析页，自动总结 → 追问一句
   - 走 AP 方案 → 先切到移动数据 → 进分析页 → 分析完再切回 `HealthMon`
   - （数据已存本地，切网不会丢；App 会给出明确提示）
10. 万一 WiFi 出问题 → 设置页切**模拟器模式**，继续演示

**保底**：模拟器模式能完整演示界面、曲线、报警；AI 需能上网（切到移动数据即可）。
